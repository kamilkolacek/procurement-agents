# Synthetic spend exports (data contract)

Generated by `make data` (`spend_classification.synth`, seed 20261108). **Never edit by hand**:
the eval gate checks every file against `evals/golden/answer_key_manifest.json`.

18 months of spend (2025-05-01 to 2026-10-31), about 20k lines and 303 fictional vendors.
All values are USD. Names, accounts and tax IDs are synthetic (`TESTACCT…`, `TESTTIN…`).

The three exports deliberately differ, the way real ERP and card feeds do: different headers,
different date formats, and messy vendor names.

## `ap_invoices.csv` — non-PO AP invoice lines
| Column | Notes |
|---|---|
| Invoice ID, Line | `INV-nnnnnn`, 1-based line number |
| Invoice Date | `MM/DD/YYYY` |
| Supplier ID | ERP supplier ID `Snnnnn`. One golden vendor has two IDs (duplicate record) |
| Supplier Name | 1-4 messy variants per supplier (case, suffix, abbreviation, typo, "- REMIT") |
| Line Description | free text; about 6% are vague ("Monthly fee"); 24 lines across AP and P-card contain prompt-injection text |
| Amount, Currency | 2-dp decimal, USD |
| Business Unit, Cost Center | CORP/SALES/RND/OPS/MFG, `CC-nnn` |
| Remit Bank Account, Supplier Tax ID | **sensitive: strip at ingest**, never send to an LLM |

About 1% of invoices are exported twice (identical rows). Ingest must dedupe them.

## `po_lines.csv` — PO lines (received)
`PO Number, PO Line, Order Date (ISO), Vendor No, Vendor, Item Code, Item Description, Qty,
Unit Price, Extended Amount, BU, Cost Ctr, Buyer`. `Item Code` is the internal item master
code, so the same code from two vendors is the same item. `Buyer` is a person's name: strip at ingest.

## `pcard_transactions.csv` — P-card
`Txn ID, Post Date (DD-Mon-YYYY), Cardholder, Merchant, MCC, Description, Amount, Dept`.
`Merchant` is a card descriptor (processor prefixes such as `SQ *` and `TST*`, store numbers,
truncation, and `AMZN Mktp US*…` codes). `Cardholder` is personal data: strip at ingest.

## `contracts.csv`
`contract_id, supplier_id, item_code, contract_price, start_date, end_date`. Fourteen contracts:
twelve are bought fully on contract (they must not be flagged), and two have planted leakage.

## Spend streams
AP, PO and P-card do not overlap: each line is spend exactly once (apart from the duplicated AP
rows above). A line's key is `AP|invoice|line`, `PO|po|line` or `PC|txn`.
